Deployment & Operations Guide

Everything that turns code on your laptop into prejemesi.cz in front of real users – the services, the secrets, the database, and where to look when something breaks. Written for your first production deployment, so it's deliberately specific. Secrets are shown as placeholders; each one tells you exactly where to find the real value.

🗺️ Architecture overview

Přejeme si is a SvelteKit app compiled to a single Cloudflare Worker (not Cloudflare Pages). The Worker talks to four external services. Everything runs on free tiers (~$0/month).

Why this matters The app has no traditional server – it's a serverless Worker that cold-starts per request. That shapes everything: connection caching must be per-request, secrets live in Cloudflare (not on a box you SSH into), and "logs" means streaming from the edge, not tailing a file.

🚀 How a change reaches production

Current setup (2026-06-13) Deployment is now automated via GitHub Actions. Merging dev → production triggers .github/workflows/deploy.yml, which builds and runs wrangler deploy. The master branch was deleted; production is the live branch.

The pipeline

work on dev→ PR dev → production→ CI checks must pass→ merge→ Actions runs wrangler deploy→ live on prejemesi.cz

dev is the integration branch (preview/work). production is exactly what's live – its tip is the running code, and git log production is your deploy history + rollback anchor. You never push to production directly (protection blocks it); you merge into it via PR.

What's wired

Piece Where Status
Deploy workflow .github/workflows/deploy.yml – on push to production + manual workflow_dispatch committed
CLOUDFLARE_API_TOKEN GitHub repo secret (used by the deploy step) set
CLOUDFLARE_ACCOUNT_ID GitHub repo variable (identifier, not a secret) set
CI gate on production ci.yml runs the checks job; required by branch protection active

Break-glass: manual deploy

The old manual path still works for emergencies (bypasses the PR gate – use sparingly). Requires a one-time wrangler login:

PowerShell · project root 
pnpm run deploy   # = vite build && wrangler deploy (deploys current local code)

The full loop for a real change

  1. Make the change on dev (or a feature branch → PR into dev).
  2. Run pnpm run check:all and pnpm run test locally – CI runs the same and gates the merge to production.
  3. If the change touches the DB schema → generate + apply the migration against Neon first (see Migrations); the deploy does not run migrations.
  4. Open a PR dev → production; once checks is green, merge. Actions deploys automatically.
  5. Watch wrangler tail for errors on the first real requests (see Logs), or the Actions run log for deploy failures.
Gate is real Because checks is a required status check on production (with admin enforcement), you cannot merge while CI is red. If a deploy isn't happening, check the dev CI run first – a failing check:all blocks the whole pipeline by design.

🌿 Branches & protection

Current model (2026-06-13) Two-branch setup: dev (integration, default) and production (live, auto-deploys). The stale master branch was deleted. Deployment is automated via GitHub Actions on merge to production – see How a change reaches prod.

CI gate

.github/workflows/ci.yml runs on push/PR to [dev, production] and executes: type-gen → check:all (paraglide + prettier + oxlint + stylelint + fallow + svelte-check + eslint) → Playwright install → vitest --coverage. The single job is named checks – that's the context required by branch protection (below).

Fast local checks, full CI gates The local pre-push hook runs typechecking and Fallow in parallel after SvelteKit preparation, targeting under a minute. Run it manually with pnpm run check:prepush. On a fresh checkout or after catalog changes, first run pnpm run paraglide:compile. Full lint and test suites remain in CI; run pnpm run check:all and the test scripts explicitly when needed. A successful push is not a full verification result. When CI is red, read the failing step in the Actions log; fix it before expecting a production merge to go through. History: the [dev, main] trigger was dead (no main branch) and was corrected; a stale oxlint-ignore-next-line directive that broke check:all was also fixed.

Branch protection confirmed via gh

Checked live with gh api repos/MartinoPolo/prejemesi/branches/<branch>/protection. The repo is PUBLIC; default branch is dev. Two protected branches now – production is hardened, dev stays light:

Resolved You asked whether to have a separate production branch – yes, and it's now set up. dev = integration (light protection, direct commits OK), production = exactly what's live (hardened: PR-gated, admin-enforced, CI-required). Trade-off to know Because production requires the checks status to be green and enforces this on admins, you cannot merge to production while CI is red – even as owner. That's the hardening working (broken code can't reach live data), but it means a failing dev CI blocks shipping. To ship past a known pre-existing CI failure in an emergency, either fix CI, use the break-glass manual pnpm run deploy, or temporarily relax the required check with gh api.

⚡ Cloudflare Workers

The Worker is configured entirely by wrangler.jsonc (committed to the repo) plus secrets stored in Cloudflare. Here is the full, real config with every line explained:

wrangler.jsonc 
{
  "$schema": "./node_modules/wrangler/config-schema.json",
  "name": "prejemesi",                         // the Worker's name in the dashboard
  "compatibility_date": "2025-05-30",            // pins Workers runtime behavior
  "compatibility_flags": ["nodejs_compat"],     // lets Node APIs (postgres driver) work
  "main": ".svelte-kit/cloudflare/_worker.js",    // build output entry (from adapter)
  "assets": {
    "binding": "ASSETS",                       // serves static files (CSS, images, JS)
    "directory": ".svelte-kit/cloudflare"
  },
  "workers_dev": false,                        // disables the *.workers.dev URL
  "preview_urls": true,                        // PR/preview deployments get URLs
  "routes": [                                  // custom domains – Cloudflare makes DNS+TLS on deploy
    { "pattern": "prejemesi.cz", "custom_domain": true },
    { "pattern": "www.prejemesi.cz", "custom_domain": true }
  ],
  "vars": {                                     // NON-secret env vars, baked into deploy
    "ORIGIN": "https://prejemesi.cz",
    "R2_PUBLIC_URL": "https://images.prejemesi.cz",
    "EMAIL_FROM": "Přejeme si <noreply@prejemesi.cz>"
  },
  "hyperdrive": [{ "binding": "HYPERDRIVE", "id": "d7f44cea901644ab84ea75b59b9f3118" }],
  "r2_buckets": [{ "binding": "R2", "bucket_name": "prejemesi-images" }]
}
vars vs secrets Anything in the "vars" block is public-ish (it ships in the deploy and is visible in the dashboard). Sensitive values – AUTH_SECRET, RESEND_API_KEY, GOOGLE_CLIENT_SECRET – are never in wrangler.jsonc. They're set via wrangler secret put and stored encrypted by Cloudflare. See Where each value lives.

The HYPERDRIVE id is not a secret

d7f44cea… is a resource identifier, not a credential – it just names which Hyperdrive config to bind. The actual database password is stored inside the Hyperdrive config on Cloudflare's side (you set it when you ran wrangler hyperdrive create). That's why the connection string never appears in the repo.

🖼️ R2 – image storage

R2 is Cloudflare's S3-compatible object store. Uploaded gift/wishlist/avatar images live in the prejemesi-images bucket and are served from images.prejemesi.cz.

How the code uses it

The binding is accessed per-request, never as a global:

src/lib/server/storage/r2.ts 
function getR2Bucket() {
  const event = getRequestEvent();
  return event?.platform?.env?.R2;   // the R2 binding from wrangler.jsonc
}

export function getPublicUrl(objectKey) {
  const publicUrl = env.R2_PUBLIC_URL;   // "https://images.prejemesi.cz"
  return publicUrl
    ? `${publicUrl}/${objectKey}`          // → images.prejemesi.cz/gifts/xyz.jpg
    : `/api/upload/${objectKey}`;          // local-dev fallback (proxied)
}

Upload-proxy pattern (not presigned URLs)

The client PUTs to /api/upload/[...path] with the file + an HMAC token. The server validates the token (signed with AUTH_SECRET), content-type, and size, then forwards the bytes to R2. Chosen for simpler auth (session cookie) and server-side validation – see .mpx/DECISIONS.md.

Upload type Folder in bucket Max size
gift image gifts/ 5 MB
wishlist banner wishlists/banners/ 10 MB
wishlist thumbnail wishlists/thumbnails/ 5 MB
avatar avatars/ 5 MB

What was set up on Cloudflare

one-time CLI setup

wrangler r2 bucket domain add prejemesi-images --domain images.prejemesi.cz --zone-id <zone-id> --min-tls 1.2 --force

R2 requires activating the $0/month metered plan once. Free tier: 10 GB storage, 1M Class A + 10M Class B ops/month, free egress.

Inspecting / managing R2

Or browse visually in the dashboard: R2 → prejemesi-images.

✉️ Resend – transactional email

Resend sends auth emails (signup verification, password reset) and notification emails (liked-gift-reserved, etc.). The wrapper degrades gracefully: no API key → it logs to the console instead of sending, so the app never crashes for lack of email.

src/lib/server/email.ts (excerpt) 
import { env } from '$env/dynamic/private';
import { Resend } from 'resend';

function getClient() {
  if (!env.RESEND_API_KEY) return undefined;   // no key → no-op (logs)
  client ??= new Resend(env.RESEND_API_KEY);
  return client;
}

function getFrom() {
  return env.EMAIL_FROM || 'onboarding@resend.dev';  // sandbox fallback
}
Idempotency Notification emails pass an idempotencyKey (e.g. notification:<id>) so retries don't double-send.

What was set up on resend.com

  1. Created a Resend account (free, no card).
  2. Added + verified the sending domain prejemesi.cz by adding the DNS records Resend provided (SPF/DKIM TXT records, in Cloudflare DNS).
  3. Created an API key → stored in Cloudflare as the RESEND_API_KEY secret.
  4. Set the production sender to Přejeme si <noreply@prejemesi.cz> via the EMAIL_FROM var.
  5. Receiving is disabled – transactional send only.
Free-tier limits 3,000 emails/month and a hard 100 emails/day cap. 1 verified domain. 30-day log retention. For a family app this is plenty, but it's a real ceiling – watch it in the Resend dashboard if usage grows.

Sandbox vs verified domain

Before a domain is verified you can only use onboarding@resend.dev, which only delivers to your own Resend account email + the *@resend.dev test addresses. Production uses the verified prejemesi.cz domain so it can email any real address.

Where to debug email

  • Resend dashboard → Emails: every send, with delivery/bounce status and the rendered HTML.
  • Resend dashboard → Logs: API errors (bad key, rate limit).
  • In wrangler tail you'll see [Email] Sent "…" (id=…) or [Email] (not sent – RESEND_API_KEY unset).

🔑 Google Auth (OAuth)

Google login is optional – the provider only registers if both GOOGLE_CLIENT_ID and GOOGLE_CLIENT_SECRET are present. Email/password works without it.

src/lib/server/auth.ts (excerpt) 
import { env } from '$env/dynamic/private';

betterAuth({
  baseURL: env.ORIGIN ?? 'http://localhost:5173',  // derives the OAuth redirect URI
  secret: env.AUTH_SECRET,
  database: drizzleAdapter(getDb(event), { provider: 'pg' }),
  socialProviders:
    env.GOOGLE_CLIENT_ID && env.GOOGLE_CLIENT_SECRET     // truthy guard – both required
      ? { google: { clientId: env.GOOGLE_CLIENT_ID, clientSecret: env.GOOGLE_CLIENT_SECRET } }
      : {},
  emailAndPassword: { enabled: true, requireEmailVerification: true },
  emailVerification: { sendOnSignUp: true }
});
Key gotcha The redirect URI is derived from ORIGIN (better-auth's baseURL), never hardcoded. So the Google Cloud Console redirect URI and your ORIGIN env var must match exactly, or login breaks with a redirect_uri_mismatch error.

What was set up on Google Cloud Console

  1. Created a Google Cloud project.
  2. OAuth consent screen: User type "External"; app name, support email, developer email. Scopes left at defaults (openid, email, profile) – no sensitive scopes means no Google verification needed. Test users added while in "Testing" status.
  3. Credentials → OAuth Client ID, type "Web application":
    • Authorized JavaScript origins: http://localhost:5173 and https://prejemesi.cz
    • Authorized redirect URIs: http://localhost:5173/api/auth/callback/google and https://prejemesi.cz/api/auth/callback/google
  4. Copied the Client ID and Client secret (secret shown once).
Status Per docs/CLOUDFLARE_SETUP.md, the production redirect URI is the one pending item – only needed if Google login is actually enabled. Verify the https://prejemesi.cz/api/auth/callback/google URI is registered before relying on Google sign-in in prod.

The auth route

A single catch-all handler at src/routes/api/auth/[...betterauth]/+server.ts forwards all /api/auth/* requests to better-auth. src/hooks.server.ts reads the session on every request and populates event.locals.user / event.locals.session.

🐘 Database – Neon + Hyperdrive + Drizzle

PostgreSQL hosted on Neon. In production the Worker reaches it through Hyperdrive (Cloudflare's connection pooler at the edge). Locally it's plain Docker Postgres. The ORM is Drizzle.

The connection logic (and the Workers gotcha)

src/lib/server/db/index.ts (essence) 
import { drizzle } from 'drizzle-orm/postgres-js';
import postgres from 'postgres';

function createDb(connectionString) {
  const client = postgres(connectionString, {
    prepare: false,        // REQUIRED through Hyperdrive/pooler
    fetch_types: false
  });
  return drizzle(client, { schema });
}

export function getDb(event) {
  const conn = getHyperdriveConnectionString(event)   // 1. platform.env.HYPERDRIVE
            ?? runtimeConnectionString                  // 2. persisted from first request
            ?? env.DATABASE_URL;                         // 3. local fallback
  // Workers: cache the client PER REQUEST (WeakMap keyed by event)
  // Node dev: cache per-process (Map keyed by conn string)
}
The bug this prevents A module-global DB client on Workers throws "Cannot perform I/O on behalf of a different request" – the socket is request-scoped. The fix (commit 9ef224c) memoizes the client per request via a WeakMap keyed by the request event. Don't reintroduce a global client.

Connection paths

Production: Worker→ Hyperdrive (pooled)→ Neon Postgres
Local: Vite→ DATABASE_URL→ Docker Postgres :5432
Migrations/inspect: your machine→ Neon direct (unpooled) string→ Neon Postgres
Golden rule Migrations and direct inspection always go to Neon's direct/unpooled endpoint – never through Hyperdrive (it's read-optimized and may cache). The runtime app uses Hyperdrive; you use the direct string.

Schema

13 tables in src/lib/server/db/schema.ts (split across modules): user, session, account, verification (auth); wishlist, priority_level, gift, gift_like, reservation; moderator_assignment, moderator_invite, wishlist_follower, notification. Drizzle runs in strict: true mode to prevent silent data loss on renames.

🔍 How to inspect the production DB

Two ways. For both you need the Neon direct connection string (see where to find it).

Option 1 – Neon's own SQL editor easiest, read-only-safe

Log in at console.neon.tech → your project → SQL Editor. Run queries directly in the browser. No local setup, no connection string handling. Great for a quick SELECT.

Option 2 – Drizzle Studio against prod powerful, be careful

Point DATABASE_URL at Neon and launch the GUI:

PowerShell · project root 
# Get the string from Neon dashboard → Connection Details → "Direct connection"
$env:DATABASE_URL = "postgresql://USER:PASSWORD@ep-xxxx.region.neon.tech/dbname?sslmode=require"
pnpm db:studio   # opens https://local.drizzle.studio in your browser
Danger Drizzle Studio can edit and delete production rows. This is real user data on a live app. Prefer Neon's SQL editor with SELECTs for inspection; only use Studio writes when you genuinely intend to change prod data, and double-check the connection string is the one you think it is.

Option 3 – any psql client

psql "postgresql://…@…neon.tech/…?sslmode=require" works too if you have psql installed.

Env you need vs. have To inspect prod you need the Neon direct connection string. You do not have it in any committed file (correctly). You get it from the Neon dashboard each time, or stash it in a gitignored local file. Your .env currently points at local Docker – don't commit a prod string into it.

💾 Migrations & backups

Schema changes (migrations)

The flow for any schema change before deploying code that depends on it:

PowerShell · project root 
# 1. Edit src/lib/server/db/schema.ts
pnpm db:generate    # writes a new SQL file into drizzle/
# 2. Review the generated SQL by hand – strict mode flags risky renames

# 3. Apply to Neon DIRECTLY (not Hyperdrive)
$env:DATABASE_URL = "postgresql://….neon.tech/db?sslmode=require"
pnpm db:migrate

# 4. THEN deploy the Worker code
Command What it does When
pnpm db:generate Creates a versioned migration SQL file Production-bound changes
pnpm db:migrate Applies pending migration files Against Neon (prod) + local
pnpm db:push Pushes schema directly, no files Fast local iteration only
pnpm db:seed Idempotent test data Local only – never prod
Memory note db:push is interactive – rename/drop prompts will hang and fail in a non-interactive shell. For production-bound changes always use the generate→review→migrate path so you see the SQL first. Ordering matters: migrate the DB before deploying code that reads the new columns, or the first requests 500.

Backups no custom system

Honest status There is no project-level backup system – no scheduled pg_dump, no backup bucket, nothing in the codebase. You are relying entirely on Neon's built-in history / Point-in-Time Restore.

What you actually have (verify in the Neon dashboard):

  • Neon History / PITR – Neon keeps a write-ahead history that lets you restore to any point within the retention window. On the free plan this window is short (commonly ~1 day; check Project → Settings → Storage/History for your exact value).
  • Neon branching – you can instantly branch the DB to a point in time, which acts like a snapshot you can inspect or promote.

Recommended to add (since this is real user data):

  1. A manual pg_dump before any risky migration:
    manual snapshot 
    pg_dump "postgresql://….neon.tech/db?sslmode=require" -Fc -f backup-$(Get-Date -f yyyyMMdd).dump
  2. Confirm the Neon retention window meets your comfort level; the paid tier extends PITR.
  3. Optionally a scheduled dump to R2 or local storage if the app grows.

🔭 When a production error happens – where to look

Current state There is no handleError hook in hooks.server.ts and no Sentry / error-tracking. Unhandled errors return a generic 500 and the only detail is whatever was console.error'd – which you read via Worker logs. This is fine for an MVP but means you must actively tail logs to debug.

1. Live tail – first thing to run

stream live prod logs 
wrangler tail prejemesi              # live console.log/error + exceptions + status codes
wrangler tail prejemesi --status error   # only failing requests
wrangler tail prejemesi --format pretty

Then reproduce the issue in the browser; the log lines appear in real time. You'll see the app's tagged logs like [Email] …, [Notification] …, and [backgroundThemeHandle] ….

2. Retained logs & metrics – the dashboard

Cloudflare dashboard → Workers & Pages → prejemesi → Logs / Observability. wrangler tail only shows logs while you're watching; for retained, searchable logs you must enable Observability.

Recommended Observability isn't enabled in wrangler.jsonc. Add this and redeploy to get retained logs + sampling you can search after the fact:
wrangler.jsonc addition 
"observability": { "enabled": true }

3. Service-specific dashboards

Symptom Where to look
500 on a page / API wrangler tail → find the thrown error + stack
DB errors / timeouts Neon dashboard → Monitoring (connections, compute, cold starts); check Hyperdrive caching if stale reads
Email not arriving Resend dashboard → Emails / Logs (delivery, bounce, rate-limit)
Login broken wrangler tail for auth errors; check ORIGIN matches the Google redirect URI
Images 404 R2 dashboard → bucket contents; verify R2_PUBLIC_URL + custom domain

4. Recommended hardening (not yet done)

  • Add a handleError hook in hooks.server.ts to log a structured error + return a friendly page.
  • Consider Sentry (free tier) for retained, alerting error tracking once you have users.

Bottom line Agents do not operate your infra through MCP today. They operate it through CLIs in the shell – and only if those CLIs are already authenticated on your machine.

What an agent can do via CLI (and the creds each needs)

Tool Capability Auth it needs
wrangler deploy, tail logs, secret list, R2 ops, hyperdrive ops Either a prior interactive wrangler login (stored OAuth token), or CLOUDFLARE_API_TOKEN + CLOUDFLARE_ACCOUNT_ID env vars.
drizzle-kit / pnpm db:* generate/apply migrations, Studio DATABASE_URL in the env (local Docker by default; Neon string for prod).
psql / Neon query prod DB Neon direct connection string.
Resend send/inspect email No CLI installed; only via RESEND_API_KEY through the app/API.
Neon (neonctl) manage DB/branches Not installed; would need neonctl auth or NEON_API_KEY.
Google OAuth config No CLI – dashboard only (human).
The interactive-login wall wrangler login, neonctl auth, and gcloud auth login open a browser and cannot be done by an agent. You run them once yourself. In Claude Code, type a command prefixed with ! wrangler login in the prompt so its output lands in the session. After that, the agent can run non-interactive wrangler commands using the stored token.

What's safe to let an agent do

  • safe wrangler tail, wrangler secret list (names only), wrangler r2 bucket list – read-only diagnostics.
  • safe Run SELECT queries against a local DB; read drizzle/ migration files.
  • supervise pnpm db:migrate against Neon, wrangler deploy, wrangler secret put – these change prod. Review the diff/SQL first.
  • never Expect an agent to print or store real secret values; .env is gitignored for a reason. Agents should reference values by name, never echo them.
Practical recipe "Debug a prod 500": you run ! wrangler login once → ask the agent to wrangler tail prejemesi --status error, reproduce in browser, and read the stack. For DB issues, paste the Neon string into the shell env yourself (or use Neon's SQL editor) and let the agent craft the SELECT.
